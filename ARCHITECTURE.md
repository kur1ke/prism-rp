# Архитектура Prism RP

> **Текущий контракт состояния:** [Единый StateTracker](docs/UNIFIED_STATE.md). Движок Scene и протокол `[scene:]` удалены без мигратора; панель «Сцена» только отображает Tracker. Ниже старые названия этапов описывают историю, если явно не обновлены.

> **Character Core / Experience (концептуальная переработка):** [восстановленные принципы, текущее состояние, открытые противоречия и критерии приёмки](docs/CHARACTER_CORE_EXPERIENCE_FOUNDATION.md). Концептуальные положения **согласованы 2026-10-26**; Core/Experience остаются **PROTOTYPE / BEHAVIOR NOT VALIDATED**. Одобрение концепции не означает, что алгоритмы, модели данных или поведение уже реализованы; открытые решения отмечены отдельно.
> **AUTO-MEMORY-REFLECTION-1 (эксперимент):** [раздельные Memory и субъективный Experience, автоматический цикл, гарантии и ограничения](docs/MEMORY_REFLECTION_EXPERIMENT.md). Реальная LLM-проверка NOT RUN, старый ручной Experience API пока сохранён только как legacy; ручной UI удалён.

Классические скрипты без сборщика модулей: каждый файл — IIFE, кладёт свой публичный API в `window.PRP`. Один и тот же код работает на Perchance, с `file://`, с GitHub Pages и в Node-тестах. `build.js` склеивает файлы в порядке тегов `<script>` из `index.html`. Этот порядок и есть порядок зависимостей.

### Условная запись результата изображения (F21)

`core/store.readModifyWrite(stores, reads, prepare)` читает записи и выполняет синхронный `prepare` внутри одной readwrite-транзакции. Он возвращает список записей или `null` для пропуска; успех/отказ сообщается после завершения всей транзакции. Хранилище не знает правил изображения и происхождения: их проверяет `images/service` в этом callback.

Pending-запись содержит `operationId` конкретного запуска. Перед сохранением результата сервис проверяет существование сообщения/свайпа/картинки, совпадение операции и её pending-статус, а также источник и предков ветки по прежним правилам. Результат меняет актуальную запись, сохраняя остальные свежие поля; сообщение и данные картинки записываются вместе. Поздний результат удалённой или заменённой операции пропускается. Поле operationId — метаданные записи изображения, не физическое состояние и не инструкция модели; версия IndexedDB не меняется.

### Согласованный экспорт бэкапа (F22)

`core/store.exportAll` читает все экспортируемые коллекции одной readonly-транзакцией и возвращает объект только после её завершения. Конкурирующая атомарная запись попадает в снимок целиком либо не попадает в него. При ошибке чтения или abort экспорт отклоняется; файл с частичными данными не скачивается. `noImages` исключает коллекцию `images` из транзакции и результата; формат бэкапа и версия базы остаются прежними.

### Основные поля карточки (F07)

`card.contextFields` содержит явные флаги description, personality, appearance и prismCore. База по умолчанию — полные описание, личность и внешность; дополнительное явное ядро выключено. Непроверенное импортированное ядро не используется даже при включённом флаге. Данные не переписываются и не исчезают при выключении. Выбор хранится в карточке/бэкапе и `extensions.prism_rp.contextFields` при CC V2/V3 экспорте.

`card-context.core` возвращает полные выбранные поля; assembler не сокращает их и включённое проверенное ядро ради бюджета. Уступают остальные слои по прежнему порядку; при нехватке — overflow до вызова модели/изменения дерева. Reflection получает тот же выбор, а подготовка начального образа Messenger уважает флаги без прежнего сокращения описания/личности. Консультационный ассистент по-прежнему читает полную карточку, его обзор Core/custom остаётся F27.

Редактор показывает текстовую оценку основных полей и обновляет её без пересоздания ввода. Цвета относительно входного окна активной RP-модели после резерва ответа: ≤20% обычный, ≤40% жёлтый, выше красный; это подсказка, не порог отказа. История, прочие слои и транспортные обёртки в этой оценке не учтены; окончательный запрос считает Prism. F09 (дубли) и оставшиеся элементы переработки карточки здесь не объявляются выполненными; F08 завершён отдельным изменением ниже; удаление «Прошлого» завершено отдельным изменением ниже.

### Поле «Прошлое» удалено

В канонической карточке, редакторе/проверке импорта, Prism, контексте ассистента и новом CC V2/V3 экспорте больше нет отдельного поля background. Биографические сведения хранятся в обычном лорбуке.

Если сохранённая карточка содержит прежний текст, `cards/service.loadAll` преобразует актуальные записи в одной read/validate/write-транзакции: поле удаляется, полный текст переносится в обычную **выключенную** запись лорбука без ключей и constant. Перенос не повторяется; отказ записи оставляет прежние данные, конкурентная правка/удаление сохраняются. Пользователь может отредактировать и включить эту запись как любую другую запись лорбука. Из URV профильная биография также сразу импортируется выключенной записью лорбука, не отдельным слотом. Старый слот не восстанавливается из расширений CC; сырой исходник по общему правилу остаётся только исходником. Это перенос текста, а не параллельная поддержка прежней механики. Версия IndexedDB остаётся v8.

### Постоянные custom-поля (F08)

Включённое пользовательское поле с mode=always передаётся целиком на каждом RP/Messenger-ходе. Оно не разбивается для выборочного отбора, не занимает место в лимите четырёх релевантных фрагментов и не отбрасывается reducer-ом ради бюджета. После допустимых сокращений остальных слоёв нехватка окна означает overflow до записи/вызова модели. Mode=relevant по-прежнему использует связь с разговором и лимит четырёх выборочных фрагментов, независимо от числа постоянных полей.

Формат карточки, импорт/экспорт и флаг enabled не меняются: импортированные custom-поля остаются выключенными до явного включения. Сведения передаются JSON-литералами с прежним уровнем власти данных, не становятся указаниями. Редактор поясняет режим «На каждом ходе целиком». Дубли между Core/полями остаются F09; оценка F07 по-прежнему показывает только основные поля/явное ядро, не полный запрос.

## Направление зависимостей

```
События DOM
   │
   ▼
ui/app.js ── корень: состояние сессии S, контекст ctx, навигация, разбор событий
   │
   ├─► ui/controllers/*  тонкие обработчики: прочитать ввод → вызвать сервис → перерисовать
   │        │
   │        ▼
   ├─► сервисы (прикладной уровень, create(ctx); DOM не трогают, перерисовку просят через ctx.ui)
   │     chat/service · prism/service · prism/memory-service · generation/service
   │     images/service · cards/service · assist/service · world/service · world/overlay-service · messenger/service
   │        │
   │        ▼
   │   чистые модули предметной области (без DOM, хранилища, сети и S)
   │     state/tracker · prism/memory-cycle · prism/scenario · prism/modes · prism/assembler · chat/tree · chat/branch
   │     messenger/time · messenger/environment · messenger/conversation
   │     cards/model · cards/ccard · cards/formats/* · cards/validate · cards/import
   │     world/model · world/lens · world/validate · world/resolve · world/overlay · world/canon · world/retrieve
   │     assist/assist · images/compose · images/compile · core/settings · core/util
   │        │
   │        ▼
   │   адаптеры: core/store (IndexedDB) · providers/openai · providers/perchance · providers/router
   │             images/backends (Perchance / A1111 / OpenAI images) · ui/files (браузерные файлы)
   │
   └─► ui/shell.js  порт интерфейса ctx.ui: модель представления, отрисовка областей,
                    поповеры, поиск, потоковая отрисовка, уведомления
                    └─► ui/views/*  чистые функции «модель → HTML»
```

Запрещённые направления: модули предметной области → интерфейс, `app.js`, хранилище или сеть; провайдеры → смысл Prism (сцена, опыт, карточки, дерево); хранилище → смысл Prism; сервис → DOM. Циклов нет: сервисы ссылаются друг на друга только через `ctx.svc`, по графу `chat ← exp, prism, images ← generation`.

### Форматы текстового транспорта

`providers/router.chat` принимает `outputFormat`: обычная RP-стенограмма (по умолчанию), `message-body` для содержимого Messenger и `json` для структурированной задачи. Perchance в `json` сохраняет system-инструкции и JSON-quoted пользовательские данные; не добавляет рамку Messenger, имена отправителей, startWith или speaker stop sequences. JSON-ответ не обрезается правилом продолжения стенограммы. Streaming и generatedText поддерживаются прежним интерфейсом. Это запрос формата, не гарантия валидности результата: проверка схемы остаётся за вызывающим сервисом.

Все четыре вызова `prism/memory-service` (extraction, текущая reflection, batch, integration) используют `json`. Семантика Memory, лимиты, бюджет, receipts и commit-порядок этим не меняются. Для OpenAI-совместимого транспорта сообщения/параметры передаются как раньше, обязательный native JSON mode не вводится. Сквозная проверка: `node tests/memory-perchance-json.js` — настоящие MemoryService/router/Perchance, подменены внешний AI и хранилище; все четыре стадии, streaming/полный ответ, невалидный JSON и ошибка провайдера. Живая модель отдельно: NOT RUN.

## Редактирование пользователя и выбор ветки

- `chat/service.editDraft` принимает только изменённый непустой текст пользовательского сообщения с активного пути. Ответ персонажа недоступен для ручной правки и в UI, и через `saveEdit`.
- Правка создаёт новый user-узел с тем же `parentId` и ссылкой `editedFrom` на оригинал. Тексты и содержимое исходного узла и его потомков сохраняются в обоих режимах. Переносятся только неизменяемая метка доставки `messengerAt` и пользовательское фото `imageDataUrl`, а извлечённые факты/коррекции старого текста не копируются.
- `generation/service.edit` владеет ходом `S.turn`, ожидает незавершённый разбор, проверяет бюджет предполагаемого пути **до записи**, атомарно сохраняет пользовательскую развилку, анализирует новый текст и запускает обычную генерацию. Повторное сохранение во время хода не создаёт второй узел. Ошибка записи оставляет старый leaf и редактор; отсутствие модели/overflow до записи не меняют дерево.
- Новые сообщения сохраняют `parentSwipeIdx` — вариант родителя на момент создания. `chat/tree.selection` восстанавливает варианты предков при возвращении к продолжению. В старых сообщениях этого поля может не быть: перед уходом или правкой текущая видимая цепочка привязывается к её выбранным вариантам в той же транзакции. Варианты других неизвестных старых веток не угадываются. Схема IndexedDB остаётся v8; дополнительные поля сообщений проходят обычный бэкап без отдельной миграции.
- `chat/service.selectBranch` сохраняет выбранные варианты и новый leaf/preview одной `mutateBatch`-транзакцией; Обновления полей варианта и привязки выполняются через `mutateBatch.patches`: запись читается и дополняется внутри той же транзакции, поэтому более свежие поля изображения/анализа не затираются старой копией. S меняется после успеха. На время операции установлен `S.turn`. Сама навигация не вызывает LLM и не переписывает историю, состояние сцены или память.
- `ui/views/branch-tree.js` отображает отдельную вкладку боковой панели; вкладка открывает модальную карту с компактными узлами и линиями (`chat/tree.layout`), без текстовых карточек на каждом узле. Контроллер обрабатывает предварительный просмотр, выбор варианта и явное подтверждение перехода; масштаб и положение принадлежат UI. Текущая ветка и точка продолжения отмечены; редактор, дерево и выбор свайпа используют одну семантику пути.
- Смена варианта исторического ответа через UI выбирает этот ответ как конец пути, сохраняя старое продолжение в дереве. Так его старые потомки не показываются как ответ на другой вариант предка.

- **Карточка** — то, что постоянно; **сценарий** — с чего начинается мир; **первое сообщение** — авторское начало; **сцена** — текущее состояние, выводимое из ветки.
## Сценарий, первое сообщение и начало сцены (FOUNDATION-B)

- **Сценарий** — исходные обстоятельства. Это не постоянная часть карточки, в сцену он не копируется и не разбирается (ни эвристикой, ни моделью). В Prism он идёт отдельным разделом «С чего начинается история».
- **Граница первого ответа** (`prism/scenario.js`, единственное место правила). Для генерации берётся ветка до генерируемого ответа: opening → `[]`, new → вся ветка, regen и continue → ветка до целевого сообщения. Если она кончается репликой пользователя, эта реплика — та, на которую отвечают. Сценарий подаётся, если в остальной части нет реплик пользователя. Значит, он доступен в начале, при ответе на первую реплику, в её другом варианте и при дописывании, а дальше не подаётся. Флага «израсходован» нет: переключение ветки или варианта пересчитывает всё заново. Предпросмотр Prism считается как следующий ответ после активной ветки.
- **Первое сообщение и альтернативные приветствия** — варианты одного корневого сообщения (`opening: "authored"`). Без вызова модели; `[scene:]` разбирается как обычно. Без первого сообщения чат создаётся пустым (`leafId = null`, без заглушек).
- **Начало сцены моделью** (`generate(null, "opening")`, только по кнопке). Порядок: сборка → проверка бюджета → вызов (поток — во временном `S.gen`, в дереве узла нет) → разбор → одна запись корневого сообщения (`opening: "generated"`) → `leafId` → сохранение. Переполнение, ошибка, отмена и пустой ответ ничего не записывают. Указание «начни сцену» — временное, вне истории, считается в бюджете. Другой вариант корневого сообщения тоже получает это указание. Реплику пользователя начало сцены не подделывает: при «одном системном сообщении» служебная «[Начало]» (нужна строгим шаблонам Mistral/Gemma, требующим первый ход пользователя) не подставляется. Perchance получает запрос только из system; OpenAI-совместимому провайдеру начало отклоняется до вызова с понятной причиной — без изменений чата.

## Мир: общий пак и линза персонажа (FOUNDATION-W1)

- **Общий пак мира** — переиспользуемое знание о мире или фандоме, общее для многих карточек. **Факт мира** — декларативное утверждение о мире. Это не указание модели, не черта характера и не опыт («Тацуки переехала в Осаку» — факт; «Орихимэ было одиноко, когда Тацуки уехала» — опыт). Не сцена («университет в Каракуре» — факт; «{{char}} сейчас в библиотеке» — сцена). Не сценарий: исходные обстоятельства в факты не переносятся.
- **Линза персонажа** — только то, что у персонажа иначе поверх одного пака: фокус, выключения (`disabledFactIds`), замены (по `targetFactId`), свои факты. Пак она не меняет и не копирует.
- **Одна линза на карточку** — ограничение хранения: уникальный индекс `cardId` в `worldLenses` и проверка сервиса. Карточку не меняли: связь «карточка → линза → пак» идёт через `lens.cardId` и `lens.packId`.
- **Порядок разрешения**:
  1. факты пака с `enabled:false` исключаются;
  2. выключения линзы исключают факты — выключение сильнее замены;
  3. к оставшимся применяются замены;
  4. добавляются свои факты линзы.

  Порядок фактов пака сохраняется, свои факты идут после. Факт после замены сохраняет id факта пака, `overrideId` указывает на замену. Ссылки на пропавшие факты — предупреждения, по тексту ничего не подбирается.
- **Режим миру не принадлежит.** В паке и линзе нет полей, зависящих от сцены или переписки.
- **Хранение**: база v4, коллекции `worldPacks` и `worldLenses` (индексы `cardId` уникальный, `packId`). Обновление только добавляет коллекции. Общий бэкап и восстановление включают их. Удаление персонажа удаляет его линзу. Пак, на который ссылаются линзы, удалить нельзя.
- **Источник истины** — только канонические поля пака и линзы. Исходник карточки, её расширения, лорбук, выключенные указания, сценарий, опыт и сцена в мир не попадают. Лорбук карточки автоматически не переносится.
- **Сам W1 в модель ничего не подаёт.** «Мир персонажа» в редакторе — статичный просмотр пака и линзы (без чата). В модель мир попадает только через W2.
- **Полная схема**: общий пак → линза персонажа → наложение мира на чат → активная ветка → адаптер режима → Prism. W1 — **общий пак + линза персонажа** (переиспользуемое знание). W2 — всё, что относится к чату и ходу.

## Мир чата: наложение, ветки, отбор и подача в Prism (FOUNDATION-W2)

- **Разделение.** Общий пак и линза — знания библиотеки и карточки (W1, редактор и «Миры»). **Наложение мира на чат** — канон конкретного чата (W2, вкладка «Мир» в панели чата). Факт мира — не опыт, не сцена, не сценарий и не карточка; ни один из них в мир сам не превращается, и мир не превращается в них.
- **Хранение.** База v5, коллекция `worldOverlays` (ключ `chatId`), одна запись на чат: `{ schema: 1, chatId, timeline, variant, entries, createdAt, updatedAt }`. Хранятся только события; собранный мир не хранится и собирается на каждый ход. Обновление v4 → v5 только добавляет коллекцию. Удаление чата (и персонажа — через его чаты) удаляет наложение; удаление линзы или пака историю чата не трогает (ссылки на пропавшие факты — предупреждения). Общий бэкап включает наложения. При восстановлении записи проверяются до записи (`world/overlay-service.checkBackup`): запись без своего чата не пишется (`overlay-orphan-chat`; при замене чат должен быть в бэкапе, при добавлении — в бэкапе или уже здесь), несколько записей для одного чата отбрасываются все (`overlay-duplicate-chat`), ничего не переназначается.
- **События** (только добавляются; исправление — новое событие, переписывания истории нет):
  - `assert` — новый факт чата со своим постоянным id факта;
  - `override` — новое значение известного факта по `targetFactId`; id факта сохраняется, у события свой id (`sourceEventId`); метаданные: не задано/`null` — наследуются, задано — заменяют; `override` убранного факта явно возвращает его;
  - `retract` — убирает известный факт с этого места.
  Цель — только по id, никогда по тексту.
- **Область.** `branch` (по умолчанию, если в чате есть сообщения) — привязка ко всей активной ветке: id сообщений от корня до листа и их выбранные варианты (`chat/branch.anchorOf`). `chat` — только по явному выбору, без подставных сообщений. Пустой чат: ветку не к чему привязать — сохранение отклоняется, область сама на «весь чат» не меняется.
- **Правило ветки** одно на опыт и мир (`chat/branch.visibleOnPath`): событие видно, только если все его сообщения на активной ветке и у них выбраны те же варианты. Соседняя ветка и другой вариант ответа (в том числе раньше места привязки) событие скрывают, но не удаляют; вернулись — мир тот же.
- **Власть** (разрешение противоречий): ветка > весь чат > линза > пак. Порядок: результат W1 (без изменений) → события «на весь чат» (по `createdAt`, затем id) → события видимой ветки в порядке повествования (глубина привязки на ветке, затем `createdAt`, затем id). Внутри слоя побеждает более позднее событие. Битые события, события к неизвестным целям и повторы id в мир не входят и видны в отчёте.
- **Таймлайн и вариант** — явные селекторы чата. Нейтральный факт (пустые метки) подходит всегда; факт с меткой — только при точно таком же выбранном селекторе (без учёта регистра и лишних пробелов); метка есть, а селектор не выбран, — не подходит. `timelineVariant` линзы остаётся пометкой линзы: его смысл (таймлайн или вариант) неоднозначен, поэтому он сам ничего не выбирает и показывается подсказкой.
- **Отбор отделён от власти** (`world/retrieve`). Власть решает, какое значение факта действует; отбор — что относится к ходу. Факт входит только при положительной связи: совпадение сущности, темы или места с текстом последних реплик; место сцены или персонаж в сцене; не меньше двух длинных слов текста факта в ходе; прозвучавшая подсказка линзы, которая есть в факте. Не дают права войти: власть слоя, недавность, принадлежность ветке, наличие в паке, имя персонажа или собеседника. Фокус линзы только поднимает подходящий факт. Порядок: прямые совпадения → сцена → фокус → слова → подсказки → исходный порядок мира → id. Не больше `worldLimit` фактов.
- **Подача в Prism.** Раздел «Релевантные факты мира» после лорбука и перед опытом. Это данные, а не указания: короткое пояснение и по одному факту на строку как литерал JSON — перевод строки, `###` или ограждения кода внутри факта не начинают новый раздел; текст факта по смыслу не меняется. Пустой отбор — раздела нет. Рамка RP не менялась.
- **Бюджет.** Факты мира — уступаемый раздел: уходят с наименее релевантного сразу после лорбука (порядок прочих уступок прежний). Не поместился ни один — раздела нет. Отчёт Prism: кандидаты, вошло, не поместилось, токены, таблица отбора.
- **Режим миру не принадлежит.** Один и тот же отбор получают сцена и переписка; у переписки нет своих фактов и своего хранения мира.
- **Только явное закрепление.** Сгенерированный текст может содержать факт, но каноном чата он становится только по явному действию пользователя («Мир» → добавить / заменить / убрать). Генерация, разбор `[scene:]`, опыт и сценарий наложение не пишут. Сборка мира для генерации только читает; переполнение, ошибка, отмена и пустой ответ мир не меняют.
- **Источник истины** — только пак, линза и явные события наложения. Исходник карточки, расширения, выключенные указания, системный промпт URV, сценарий, сцена, опыт, ответ модели и сведения импорта в мир не попадают.

## Переписка: среда, время и состояние (FOUNDATION-C)

- **Режим чата фиксирован.** Сцена (`rp`) или переписка (`messenger`) выбираются при создании и не меняются: переключателя в чате нет. Одна карточка может иметь и сцену, и переписку — это разные миры; ничего между ними не переносится. Старые чаты сохраняют записанный режим, ничего не делится и не угадывается.
- **Адаптер режима** (`prism/modes`): RP получает данные `StateTracker.describe(snapshot)`; Messenger — положение, состояние переписки и время. Старого протокола Scene нет. Бюджет и разделение данных/указаний остаются в assembler.
- **Среда переписки** — текущие обстоятельства персонажа вне переписки (где, чем занят, кто рядом, что происходит, доступность). Это не факт мира, не сцена и не опыт. Хранение: база v6, коллекция `messengerEnvironments` (ключ `chatId`), одна запись на чат-переписку: `{ schema: 1, chatId, timeZone, timeMode, manualNow, events, conversationEvents, createdAt, updatedAt }`. У сцены записи нет. Итоговое положение не хранится — оно собирается по ветке.
- **События положения**: `{ id, scope, patch, provenance, effectiveAt, note, createdAt }`. Ключа нет в `patch` — значение не меняется; `null`, `""`, `[]` — очищают. Область `branch` (привязка ко всей активной ветке, `chat/branch.anchorOf`) по умолчанию, `chat` — только явно; без сообщений привязать к ветке нельзя, на «всю переписку» само не меняется. Видимость — то же правило ветки, что у опыта и мира чата. Порядок: события всей переписки (по `effectiveAt`, затем `createdAt`, затем id), затем события ветки в порядке повествования (глубина привязки, затем то же). Событие с `effectiveAt` позже текущего момента ещё не действует.
- **Доступность** (`available` / `busy` / `away` / `unknown`) — контекст для ответа, а не запрет: в Prism подаётся с пометкой, что не запрещает ответить.
- **Время.** Пояс чата (IANA) и режим: `live` — «сейчас» берётся из часов в момент действия (`ctx.clock`, в тестах подставные); `manual` — сохранённое время, меняется только явно («+15 мин», поле времени). Таймеров и фонового хода времени нет.
- **Метки сообщений неизменяемы.** У варианта переписки — `messengerAt: { at, timeZone, world }`: момент и положение персонажа на ветке перед сообщением (мир — пак, линза, наложение — не копируется). Пишется при отправке пользователем и при успешном ответе модели; момент ответа выбирается при подготовке. Новый вариант — своя метка; переключение вариантов переключает метку; «продолжить» метку не меняет (ставит только отсутствующую); правка текста метку не трогает. Ошибка, отмена, пустой ответ и переполнение метку не пишут и время не двигают. У старых сообщений без метки время неизвестно (время записи не подставляется).
- **Состояние переписки** выводится из активной ветки каждый раз: кто писал последним, сколько сообщений без ответа, время последнего сообщения и сколько прошло, открыта ли переписка и почему (`empty`, `awaiting-character`, `awaiting-user` — вопрос в последнем ответе, `idle`, `quiet` — 12 ч и больше после ответа). Договорённости (обещания и планы) — только явные отметки пользователя с правилом ветки; из текста ничего не извлекается.
- **Прошедшее время ничего не устанавливает.** В Prism подаётся «что происходило за это время, неизвестно, если об этом не сказано». Нет симуляции, расписаний, сна, поездок, событий «вне кадра» и сообщений по инициативе персонажа.
- **Генерация читает среду, но не пишет её.** Положение, договорённости и время меняются только явными действиями во вкладке «Среда».
- **Бюджет.** Неуступаемое ядро переписки: рамка, где / чем занят / доступность, состояние переписки, текущее время и время последнего сообщения. Уступки (после фактов мира, до опыта): сначала договорённости со старых, затем списки «рядом» и «происходит». Порядок прочих уступок прежний.
- **Удаление и бэкап.** Удаление переписки (и персонажа — через его чаты) удаляет её среду; пак, линза и мир чата её не трогают. Бэкап включает среды. Восстановление проверяет до записи: среда только для переписки из бэкапа (замена) или из бэкапа и уже существующих (добавление); для сцены, сироты и повторы одного чата — отбрасываются, ничего не переназначается. При добавлении местный чат главнее входящего с тем же id: если режимы различаются, входящий чат отклоняется до записи вместе с его сообщениями, картинками, опытом, наложением мира и средой (`chat-mode-conflict`, `chat/service.checkBackupChats`); среда для существующего чата проверяется по его местному режиму.
- **Старая переписка без среды** открывается с пустой средой в памяти (всё неизвестно, живое время, пояс браузера); запись появляется только при явной правке.

## Memory: несколько эпизодов одного источника (F11)

`prism/memory-cycle` проверяет каждый event/quote и отличает эпизод от сообщения:
один messageId может дать несколько самостоятельных Memory (до четырёх за запрос).
`recent`, Reflection, панель и группы Experience сохраняют разные event одного
источника, исключая только точные нормализованные повторы; при одинаковом времени
порядок стабилизируется ID. Семантическая дедупликация остаётся задачей extractor.
`prism/memory-service` записывает все Memory вместе с одной source-once отметкой;
ветка, swipe, полный текст и цепочка предков определяют прежние границы источника.
Новых коллекций, миграций и скрытых указаний не добавляется. Контракт и проверки:
[Memory/Reflection](docs/MEMORY_REFLECTION_EXPERIMENT.md), `tests/memory-episodes.js`.

## Границы Prism и ядро карточки (FOUNDATION-H)

- **StateTracker** владеет состоянием участников и общей RP-обстановкой. Панель «Сцена» читает его snapshot; независимого fold/parser Scene нет. См. актуальный контракт выше.
- **Данные и указания** (`prism/data`).
  - Указания — только «Указания автора карточки…» (до и после истории) и «Служебные указания для этого ответа»: протокол сцены и рисования, «продолжи», «начни сцену». Они идут как есть.
  - Всё остальное подаётся разделами-данными: карточка (ядро и подробности), примеры речи, персона, лорбук, факты мира, опыт, сценарий, сцена, среда переписки (положение, состояние, время).
  - Раздел-данные начинается с пометки `[данные · …]`. Значения — литералы JSON в одной строке, подписи пишет только код.
  - Перевод строки, `###` или «Игнорируй систему» в тексте пользователя или файла не создают раздел и не становятся указанием. Текст не меняется по смыслу: ничего не вырезается и не переписывается, проверки моделью нет.
  - Имена в заголовках однострочные.
  - Рамка обоих режимов содержит общее правило чтения разделов (`prism/modes.DATA_RULE`).
  - При «одном системном сообщении» разделы и пометки те же.
- **Эпистемический статус** — лёгкий словарь, используется там, где он нужен смыслу:
  - ESTABLISHED — явная сцена, действующий факт мира, поле среды;
  - DERIVED — состояние переписки, прошедшее время;
  - INTERPRETATION — настроение в сцене и субъективное восприятие Experience;
  - UNKNOWN — пустое не заполняется значением по умолчанию.
- **Experience** — автоматическая субъективная рефлексия из `prism/memory-service.experience(path)`, передаётся как JSON-литерал восприятия. Старый ручной Experience удалён: нет сервисов редактора, миграции, ранжирования, загрузки для чата или fallback в Prism. Коллекция IndexedDB `experience` остаётся пассивным архивом для бэкапов и удаления записей вместе с владельцем; старые тексты не подаются модели. Версия IndexedDB не меняется.
- **Карточка** — источник устойчивой истины о персонаже, её поля не меняются.
- **Ядро для Prism** (`card.prismCore`, `prism/card-context`) — необязательные дополнительные сведения, включаются отдельной галочкой (по умолчанию выключено). Импортированное ядро требует проверки. Сборка из карточки копирует полный текст без модели; очистка не создаёт запасного усечённого ядра.
- **Основные поля.** Выбранные description/personality/appearance передаются целиком. Во включённом проверенном Core исключаются только полные точные совпадения с выбранными основными полями или их абзацами после подстановки макросов; исходная карточка не меняется. Та же чистая проекция используется Reflection и начальным образом Messenger. Исключённые элементы перечисляются в report.card.core.duplicates; смыслового сравнения нет. Предела 600 символов и сокращения ядра ради бюджета нет; при нехватке окна — overflow.
- **Дополнительные сведения.** Включённые custom-поля в режиме relevant используют отбор не более четырёх связанных фрагментов; mode=always передаёт весь текст без этого лимита и бюджетного усечения. Отдельного background-слоя нет; биография — обычный лорбук. Настройки изображений в card.image остаются отдельными визуальными данными.
- **Примеры речи** по числу ответов персонажа на ветке: 0–2 — все, 3–5 — первый, 6 и больше — ни одного.
- **Лорбук** — справка карточки низкого приоритета.
  - Подаётся одним разделом после персоны: записи «до персонажа» — первыми.
  - Пометка раздела говорит, что при расхождении с фактами мира этого чата верны факты мира. Пометка мира говорит то же с его стороны.
  - Противоречия не подавляются молча и не угадываются.
  - Импорт сохраняет флаг `enabled` из файла: лорбук — данные, а не указание, поэтому карантин указаний к нему не применяется. Решение принято, чтобы не ломать существующие карточки.
  - Лорбук остаётся в карточке; паки сам не создаёт.
- **Власть знаний о мире:** канон чата и ветки > линза персонажа (замены, свои факты) > общий пак > лорбук карточки > неизвестно.
- **Порядок Prism:**
  1. рамка;
  2. указания автора;
  3. ядро карточки и автоматический субъективный Experience;
  4. подробности карточки;
  5. примеры речи;
  6. персона;
  7. лорбук;
  8. факты мира;
  9. сценарий, пока действует;
  10. сцена или среда переписки;
  11. история;
  12. указания автора после истории;
  13. служебные указания ответа.
- **Бюджет.** Уступки идут в таком порядке:
  1. старая история;
  2. примеры речи, с последнего;
  3. подробности карточки, с наименее связанной;
  4. лорбук;
  5. факты мира;
  6. договорённости переписки;
  7. списки «рядом» и «происходит»;
  8. автоматический Experience;
  9. указания после истории;
  10. персона, сценарий, указания автора, вторичное ядро (устойчивое, манера речи, черты сверх первой, хвосты по предложениям);
  11. история до последнего сообщения.

  Не режутся: рамка, минимум ядра (имя, первое предложение), сцена или ядро переписки, служебные указания. Иначе — OVERFLOW: 0 вызовов модели, ничего не записывается.
  - Отчёт Prism (`report.card`) показывает: ядро (явное или запасное, токены, сокращения), кандидатов подробностей с причинами и судьбой (в контексте / не поместилось / сверх лимита / не относится), примеры (сколько, по какому правилу), счётчик устаревших операций сцены.
- **Режимы.** У переписки сцены нет: общие RP time/weather/present не допускаются; действуют отдельное время переписки и reported-сведения из того же Tracker.
  - Картинки переписки строятся из `[draw:]`, карточки и персоны. Одежду и место из сцены RP они не берут; «вне кадра» ничего не придумывается.
  - **Граница визуальных источников (IMG-STATE-SHOT):** `images/compose` разделяет явный `shot` (`scene`), физические сведения `stateContext` (из snapshot выбранного пути/свайпа) и неизменяемые теги `fixedKeep` (настроенные visual look/wardrobe/pov-теги; технические Card trigger и LoRA подключаются независимо в `finalise`) от старого общего `keep`. Прежнее `keep` сохраняется для fallback без перевода. Увиденная в кадре одежда не дублируется состоянием; для `camera=owner` прежняя поза/занятие владельца камеры не приписывается изображению. При реальном переводе `images/service` передаёт `stateContext` как JSON-quoted данные в **тот же** запрос `images/compile`, где явный shot имеет приоритет, а физический контекст используется только если визуально применим. Успешный перевод заменяет сырые данные (`stateCompiled`); русский слой не конкатенируется после него. Cache key включает контекст состояния, поэтому разные снимки не используют общий перевод. Если перевод отключён/сбой, старые слои fallback видны как прежде; происхождение в `promptSources` не меняет канон. Эти сведения — контекст, не инструкции для модели; финальная LoRA/trigger остаётся отдельным стабильным техническим слоем.
  - Ассистент берёт строку сцены только у сцены RP.
  - Картинки — производное: в Prism не возвращаются.
- **Бэкап.**
  - «Заменить» — весь набор данных Prism RP, **атомарно**. Одна транзакция `readwrite` на все известные коллекции (`core/store.STORES`, включая настройки). В ней синхронно, без `await` между запросами, ставятся `clear()` каждой коллекции и `put()` каждой записи бэкапа.
    - Успех — только по `oncomplete` транзакции. Коллекции нет в файле — после замены она пустая.
    - Ошибка любого запроса (например, нарушение уникального индекса) или исключение при постановке в очередь (запись без ключа) прерывает транзакцию целиком. Все коллекции остаются как были, промис отклоняется, интерфейс показывает «Бэкап не загружен… Данные не изменены» и позволяет повторить.
    - Сама база не удаляется, версия схемы и жизненный цикл соединения (DB_BLOCKED, таймаут, versionchange) прежние.
  - «Добавить» — той же одной транзакцией, только `put()`, тоже атомарно: при ошибке не добавляется ничего.
  - До записи `core/backup.check` отклоняет повторы id и записи без своего персонажа, чата или пака. Две линзы одного персонажа отклоняются, в том числе при добавлении поверх существующей. Ничего не переназначается.
  - Мир чата, среда переписки и конфликт режима проверяются прежними проверками сервисов уже по проверенному списку чатов.
  - «Добавить» работает как раньше.

## VIS-OUTFIT-1A — физическое отсутствие снятых вещей (foundation, testing)

- Предшествующая спецификация: приложенный диалог пользователя `VIS-OUTFIT-1`. Полная цель — `CurrentOutfit` (named wardrobe or inline), `WearState` (`worn`, `removed`, `partiallyWorn`), отдельный Card wardrobe dictionary и shot-only `[draw:]`. Полная стадия **ещё не закрыта**.
- Первый срез восстанавливает отсутствующий инвариант: `wear.remove` из явно подтверждённого сообщения остаётся фактом отсутствия конкретного предмета, даже если исходный список `wear` неизвестен. `wear` при этом остаётся неизвестным, а не превращается в вымышленный пустой комплект. Происхождение каждого absent-факта — id сообщения, свайп, роль и точная цитата. В `wear.add` предмет снова надет, явный полный `wear.set`/сброс сбрасывает прежнее отсутствие.
- Источник истины — существующие `stateEvents` выбранного сообщения и `stateCorrections`, результат свёртки в `stateTracker.fold`. Нового persisted store, schema, actor ownership, инвентаря или записи в Card нет. Подтверждённые absent-факты поступают в `prism/assembler` как JSON-quoted данные внутри строгого preflight budget, а не как инструкции персонажу. Они сохраняются после выпадения исходного raw-текста из бюджетного контекста.
- **Неполный контракт:** текущее `wear` остаётся плоским списком; состояние частично смещённых вещей, named outfit refs, перевод item-specific negative image tags, авторитет разрешения конфликтов изображения и точность живого LLM-наблюдателя ещё не реализованы. Не утверждать, что VIS-OUTFIT-1 закрыт или что Image Compiler уже перестал дорисовывать снятые предметы.
- Не подменять историю/свайпы, не выдавать намерения за действия и не делать вывод об открытых частях тела только из отсутствия отдельной вещи под верхней одеждой.

## Инициатива в переписке (FOUNDATION-D)

- **Только переписка и только по явному действию пользователя.** Кнопка «Проверить инициативу» у поля ввода переписки. В сцене (RP) её нет.
  - Нет таймеров, опроса, фоновой генерации, уведомлений и расписаний.
  - Проверка спрашивает, написал(а) бы персонаж сейчас сам(а). Она не приказывает писать.
- **Три разных вопроса** (`messenger/initiative`):
  1. **Допустимость** — можно ли проверять. Сама по себе это не желание персонажа. Условия:
     - переписка, есть персонаж, нет идущей генерации, подключена модель;
     - последним писал(а) не пользователь (`reply-pending`: иначе это обычный ответ);
     - на активном пути после последней реплики пользователя ещё нет сообщения-инициативы (`already-initiated`). Это правило по структуре ветки, без времени и скрытых счётчиков. Сообщение на другой ветке не мешает;
     - транспорт принимает запрос без хода пользователя (`needs-user-first`, см. ниже).
  2. **Возможные поводы** — детерминированно, только из уже известного:
     - открытые договорённости пользователя (ESTABLISHED, до 5);
     - молчание с последнего сообщения не меньше 12 ч по времени переписки (DERIVED). Это повод, а не условие проверки; при неизвестном времени последнего сообщения его нет.

     Срок договорённости не угадывается: в модели договорённостей нет времени, «завтра» не становится датой. Внешних поводов нет — так и сказано; личный повод модель выводит из характера и опыта, выдуманные события вне переписки запрещены.
  3. **Решение** принимает модель: текст сообщения или ровно `[no-message]`.
- **Prism.** Обычная сборка переписки: ядро и подробности карточки, опыт, мир, среда, состояние переписки, время, история, указания автора. К ней добавляются:
  - раздел-данные «Возможные поводы написать первым» (литералы `prism/data`; неуступаемый — он мал);
  - временное указание в «Служебных указаниях для этого ответа»: пользователь ничего не присылал, молчание — нормальный выбор, время и договорённости — сведения, а не приказ, ничего не выдумывать вне переписки, не писать за пользователя, отказ — ровно `[no-message]`.

  Реплика пользователя не подделывается. Указание в историю не попадает. Всё считается в строгом бюджете; переполнение — 0 вызовов, 0 записей.
- **Разбор ответа.** После отделения рассуждения, `[scene:]` (в переписке он неактивен) и `[draw:]`:
  - весь ответ, без пробелов по краям и без учёта регистра, равен `[no-message]` → отказ;
  - пусто → пустой ответ;
  - маркер внутри текста → испорченный ответ;
  - иначе → сообщение.

  Служебный маркер в историю не сохраняется никогда.
- **Запись** (одна, после ответа, как у начала сцены).
  - Перед записью сверяются чат и активный путь с выбранными вариантами. Если пока шёл запрос они сменились — ничего не записывается (`stale`).
  - Успех — одно обычное сообщение персонажа (несколько пузырей одного ответа — одна логическая единица, как в FOUNDATION-C):
    - `messengerAt` — момент, выбранный при подготовке (живое время не пересчитывается после ответа; ручное — сохранённое, само не сдвигается);
    - происхождение на варианте `initiative: { schema: 1, trigger: "user-check", reasonIds }` — только метаданные, не факт мира и не опыт.
  - Договорённости сами не закрываются; среда, мир, опыт, сцена и карточка не меняются.
- **Ничего не записывают:** отказ (только временное уведомление «Персонаж решил пока не писать», без записи и без запрета на следующую проверку), ошибка провайдера, отмена, пустой или испорченный ответ, смена чата или ветки, недопустимость, переполнение. Ошибка провайдера и молчание персонажа — разные исходы.
- **Варианты, продолжение, удаление.**
  - «Другой вариант» у сообщения-инициативы — снова проверка инициативы, с тем же указанием. Новый вариант той же логической единицы записывается только при успехе и получает свои метку и происхождение; отказ варианта не добавляет.
  - «Продолжить» — обычное продолжение, происхождение сохраняется.
  - Удаление — обычное: после удаления сообщения-инициативы проверка снова допустима.
  - Вариант не делает допустимой вторую инициативу подряд.
- **Параллельность.** Общий замок генерации (`S.gen`) ставится синхронно до первого ожидания и держится до конца записи (сообщение, `leafId`, превью чата). Снимается в `finally`, в том числе при ошибке хранилища, и только если это тот же замок.
  - Повторный клик и обычная генерация во время проверки или сохранения отклоняются (`busy`), кнопка неактивна.
  - Сообщение (или новый вариант) и чат (`leafId`, превью) пишутся **одной транзакцией IndexedDB** (`core/store.putAll` через `chat/service.commitMessage`): всё или ничего. Память (`S.messages`, текущий чат) меняется только после успеха. При отказе любой из двух записей нет ни сообщения, ни варианта, ни нового `leafId` или превью — ни в базе, ни в памяти.
  - «Другой вариант» — только у сообщения на активной ветке (`not-on-path` — отказ до вызова).
- **Транспорт.**
  - OpenAI-совместимый, обычный режим: запрос заканчивается историей и служебными указаниями.
  - Режим «Одно системное сообщение» у OpenAI-совместимого сервера: строгому шаблону нужен ход пользователя последним — отказ до вызова (`needs-user-first`), без подделки.
  - Perchance: в Messenger история сериализована как JSON-строки с `role`/`content`, без именных строк стенограммы; формат ответа `message-body` не задаёт `Имя:` в `startWith`. Указание проверки идёт после истории как служебный текст, последняя строка — `closing` с решением инициативы, без искусственной реплики пользователя. В RP прежняя именная стенограмма сохраняется. `generatedText` не может повторно добавить `startWith`, если поток уже получен (поток — источник отображаемого текста; при отсутствии потока удаляется только точный технический префикс продолжения). Система никогда не вырезает реальные упоминания имён из сообщений регулярными выражениями.
- **Хранение и бэкап.** Нового хранилища и смены схемы нет: происхождение лежит в варианте сообщения, переживает бэкап (атомарная замена FOUNDATION-H), повтор id в бэкапе отклоняется. Старые сообщения в инициативу не превращаются.
- **Не делается:** автономные и фоновые сообщения, таймеры, отношения, процедурный мир, инициатива в RP, сроки договорённостей, автоматическое закрытие договорённостей, запись отказов.

## Формат карточек и расширяемые поля (CARD-Q — кандидат для testing)

- Каноническая модель остаётся `cards/model.js`; `description`, `appearance`, `personality` и `scenario` различаются семантически; отдельного `background` больше нет, биография хранится в лорбуке. Нельзя заменять одно другим при импорте.
- `customFields` — массив `{id,label,text,mode,enabled}`. При импорте V2/V3 все поля приходят с `enabled:false` даже если источник просил включить их. Пользователь включает каждое поле через явную галочку.
- Пользовательские поля поступают в RP **только** как обычные данные через `prism/card-context.chunks/select` и `prism/data`. `mode:"always"` повышает приоритет отбора, но действует тот же предел подробностей, жёсткий токен-бюджет и обычный порядок сброса. Поле не становится author directive.
- V2/V3 экспортируются через `cards/ccard`: стандартные поля в `data`, а `extensions.prism_rp.fields` (включая пустые строки), `extensions.prism_rp.image` (объявленные пустые слоты), `extensions.prism_rp.customFields` (включая пустой массив) — всегда. `description` включает маркированный абзац `Внешность` для сторонних клиентов. Биография экспортируется только обычной записью character_book; отдельный слот или специальный разбор «Прошлого» не восстанавливается.
- Структуры, специфические для других приложений, сохраняются в `card.source.raw` и не становятся выполненными инструкциями.
- `image.loraAdvanced.enabled` управляет применением `image.loraAdvanced.rules`; выключение галочки сохраняет правила как текст, но выключает их действие. Импорт принудительно выключает эти правила. В режиме камеры владельца (`camera=owner`) триггер и LoRA сохраняются, но полное лицо/портрет не навязываются.
- Представление карточки остаётся в `ui/views/card-editor.js`, обработка — в `ui/controllers/cards.js`; новые панели используют семантические подгруппы без верхнеуровневых вкладок.
- Спецификация соответствий: `docs/CARD_FORMAT_COMPATIBILITY.md`. Памятка для пользователей и AI-редакторов: `docs/CARD_EDITOR_GUIDE.md`. **Не встраивать памятку в карточку или игровой контекст**.

## Ход после ответа: разбор состояния и очередь отправки (PERF-01)

- **Порядок хода.** `generation/service.send`:
  1. дождаться разборов этого чата;
  2. сверить чат и путь (сообщения + выбранные свайпы) с моментом нажатия;
  3. записать реплику;
  4. разобрать её (`state.track`) и дождаться всех разборов чата;
  5. RP-генерация;
  6. ответ записан и показан, замок `S.gen` и ход сняты;
  7. разбор ответа и затем авто-картинка (`afterReply`) идут отдельно и не держат ввод.
- **Картинка привязана к своему варианту.** `afterReply` в момент ответа фиксирует объект свайпа, его номер и текст. После разбора картинка рисуется только в тот же вариант и только если:
  - он всё ещё выбран;
  - его текст не менялся;
  - директива `[draw:]` принадлежит ему;
  - сообщение на активной ветке и весь путь **до него включительно** (предки, их выбранные свайпы и текст) тот же, что в момент ответа (смена свайпа предка не убирает потомка с пути, но меняет контекст ответа);
  - разбор не был отброшен как устаревший (`stale-branch`).
  Иначе авто-картинка пропускается (`imageSkipped` в «Таймингах») и ни в какой вариант не попадает. Нарисовать вручную можно кнопкой «Нарисовать».
- **Зависимость сохранена.** Следующая RP-сборка и картинка читают `stateEvents`. Поэтому новая генерация (в том числе «Другой вариант», «Продолжить», начало сцены, проверка инициативы) не стартует, пока у чата есть незавершённый разбор: она видимо ждёт (`S.turn.phase = "waiting-state"`, статус у поля ввода). Параллельных запросов в этом этапе нет.
- **Очередь без фиктивных узлов.** Реплика, принятая во время разбора, живёт только в `S.turn` (память). В дереве её нет, пока не прошла сверка.
  - Смена чата, ветки или свайпа, удаление сообщения пути или «Отменить» — реплика не пишется.
  - Текст возвращается в поле ввода своего чата (`ui.restoreDraft`, `S.sendDrafts`).
  - Второе нажатие, пока ход этого чата не завершён, ничего не делает.
  - Ключ хода (`turnKey`): id сообщений пути, выбранные свайпы и отпечаток текста каждого из них. Правка любого сообщения активной ветки во время ожидания — другой контекст: реплика не отправляется, текст возвращается. Правка вне активной ветки на ход не влияет.
  - Поле ввода принадлежит своему чату (`data-chat`). При уходе из чата в любой другой вид (другой чат, ассистент, «Персонажи», мир) набранное сохраняется черновиком этого чата (`S.sendDrafts`) и возвращается при открытии, в другой чат не переносится.
  - Перезагрузка страницы теряет ещё не записанную реплику.
- **Разбор как задача.** `state/service.track`:
  - одна задача на (чат, сообщение, свайп, текст);
  - никогда не отклоняется (ошибки становятся результатом);
  - `pending(chatId)` и `settle(chatId)` — ожидание, ограниченное таймаутом наблюдателя плюс 5 с.
  - Проверка актуальности внутри `observeMessage` не изменена: результат пишется только в тот же чат, свайп и текст при неизменном пути. Очередь как раз не меняет путь до конца разбора.
- **Диагностика.** `core/perf.js` хранит в памяти до 80 записей. Каждая запись — только метрика, число мс, id сообщения и чата, короткий исход.
  - Метрики: `userStateMs`, `roleplayMs`, `assistantStateMs`, `imagePrepareMs`, `readyAfterReplyMs`, `sendToRoleplayMs`.
  - Показ: Debug → «Тайминги» (режим разработчика). При смене chatId журнал очищается на месте; проверка activeChatId в `core/perf.js` отбрасывает поздние метрики другого чата. В `generation/service.js` все записи временных этапов содержат chatId. Смена раздела интерфейса или повторное открытие того же чата не очищает журнал.
  - Все пять разделов Debug имеют единый обработчик «Копировать» в контроллере панели, который копирует видимый текст активного раздела через Clipboard API с fallback для Perchance. Данные не экспортируются и не сохраняются автоматически.
- **Ограничения.**
  - Время до следующего RP-запроса уменьшается только на время набора, перекрытое разбором. Мгновенная отправка ждёт столько же, сколько раньше.
  - Разбор ответа, прерванный уходом в другой чат, отбрасывается и сам не повторяется (как и раньше; «Повторить анализ» — в Debug переписки).

## PERF-02A — независимый Processing Provider

- **RP Provider:** `settings.activeProvider`, `ctx.provider()`. Только художественная генерация, opening, initiative, regen и continue.
- **Processing Provider:** `settings.processingProvider`, `ctx.processingProvider()`. `StateTracker` (реплики пользователя, персонажа, правки и retry) и `Image Compiler` используют его независимо от RP.
- **Совместимость:** пустое значение `processingProvider: ""` означает наследование RP Provider. Отсутствующий сохранённый id тоже временно использует RP Provider, но UI предупреждает; удаление выбранного API сбрасывает обработчик в режим наследования.
- **Границы:** изменение настроек не меняет контекст RP, budget или sampler; модель обработки не записывает события напрямую и не обходит `state.observeMessage`. Provider фиксируется на время соответствующей асинхронной операции; дальнейшее переключение модели не перенаправляет уже начатый запрос.
- **Задержки:** PERF-02A не меняет последовательность `StateTracker → RP → StateTracker`, не создаёт параллельных запросов и не заявляет ускорение само по себе. Для этого потребуется отдельный контракт зависимостей и измерения PERF-02B.

## PERF-02B (эксперимент) — перекрытие двух независимых Observer-запросов

- **Условие:** предыдущий анализ состояния ещё выполняется, а у нового хода Processing Provider явно отличается от RP Provider. Режим наследования сохраняет прежнюю последовательность.
- **Read-only preparation:** `state.prepareUser(text, provider)` запускает извлечение фактов из текста ожидающей реплики. Он не создаёт сообщение, не пишет `stateEvents` и не меняет Scene/World/Experience.
- **Gate перед записью:** `generation.send` по-прежнему ждёт завершения старого Observer, сверяет чат/путь/выбранные свайпы/тексты, и только после успешной сверки записывает сообщение пользователя.
- **Коммит:** `state.observeMessage` повторно сверяет роль, режим, текст, имя собеседника, chatId и provider ID предварительного результата. При несоответствии выполняется обычный анализ. Сохранение фактов остаётся в прежнем обработчике и с прежними проверками происхождения; RP-сборка начинается только после подтверждения состояния.
- **Отмена и ошибки:** при отмене или устаревании ветки предварительный ответ отбрасывается; внешняя модель может закончить уже запущенный read-only запрос, но он не имеет пути для самостоятельного коммита. Таймаут и ошибку фиксирует прежний Observer.
- **Ограничения:** дополнительный одновременный запрос способен увеличить нагрузку на Processing Provider; `ai-text-plugin` может самостоятельно сериализовать вызовы. `sendToRoleplayMs` измеряет фактический эффект; без одинаковых живых сценариев до/после нельзя утверждать ускорение. Графический backend и изображение после подтверждённого состояния не параллелизованы.

### Observer context references (VIS-REF-1, testing)

- Наблюдатель анализирует действие из **текущего сообщения**, а предыдущие пять записей выбранного пути и референты из текущего `StateTracker` передаются только как JSON-quoted данные; они не становятся инструкциями и не доказывают факт действия.
- `wearState.worn` — вычисленный при `fold` индекс уже названных надетых вещей с per-item `source`. Не новый persisted store. Ссылка `referenceId` выбирается из его кандидатов и после разбора материализуется как `reference` вместе с текстовым `value`. Никакие произвольные названия модели или `value`, не совпадающие с кандидатом, не принимаются. `stateTracker.apply` **повторно валидирует** ссылку относительно предшествующего состояния каждого сообщения активной ветки; смена свайпа/предка или удаление старой вещи автоматически делает ссылку недействительной.
- `evidence` относится только к **текущей реплике**, а `reference.source` к ранее установленному объекту; ни роль собеседника, ни импортированный текст не могут менять другого актёра. Messenger оставляет `reported`, RP — `established` только при реальном действии. При неоднозначности модель обязана сообщить `unresolved` и не возвращать событие.
- Снятие по местоимению сейчас поддержано только для `wear.remove`, остальные типы сущностей будут подключаться через тот же typed reference contract после отдельных тестов. Это **не** regex по словам «сняла её». Переиспользование speculative `prepareUser` учитывает значения истории и ссылок; запись результата запрещена, если тексты, события или свайпы предков изменились во время запроса. Отдельный контекст занимает ограниченное место в запросе Observer, штатный Prism preflight для RP остаётся прежним.
- Debug → Трекер показывает подтверждённые снятые вещи, `certainty`, `messageId`, `swipeIdx` и цитату. В Debug → Ошибки неоднозначность видна как причина отсутствия события. **Проверка живой модели ещё требуется**: инструкции и структурная проверка не гарантируют, что модель правильно определит каждое местоимение.


## StateResolver — единая read-only проекция (SR-1, testing)

- `js/state/tracker.js` остаётся **единственным детерминированным источником** физических фактов: fold по выбранному пути/свайпам, certainty, происхождение и отсутствие предметов. `js/state/service.js` собирает его snapshot. `Observer`, State Tool и ручные коррекции дают события единого формата. Legacy Scene удалена без адаптера.
- `state/resolver.js` форматирует только сообщения Messenger и их давность; RP, панель, изображения и ассистент читают Tracker напрямую.
- Область этого PR — без смены внешней семантики. `CurrentOutfit`/`partiallyWorn`, консолидация `fields.wear` + `wearState.worn`, типизированные scene/state events и negative image tags **не внедрены**. Не сливать эти этапы в рефакторинг и не объявлять VIS-OUTFIT-1 закрытым.
- Данные legacy Environment остаются начальным слоем; неизвестные поля StateTracker не затирают старые значения. Новая проекция не меняет stored schema/DB, canon, ветку, World, Experience, Card или строгий token preflight.



### Согласованная активация чата (F18)

`ui/app.activateChat` читает сообщения, Memory, наложение мира, Messenger и картинки
во временные значения. `memoryService.read`, `worldOverlayService.read`,
`messengerService.read` не меняют активное состояние; `imageService.readForChat`
возвращает URL и отмечает прерванные картинки только в переданном наборе сообщений.
Существующие `load`-методы продолжают обслуживать явную загрузку сервисов.

После успешного чтения проверяются актуальность намерения навигации, существование
чата и отсутствие начатого хода; затем ID, карточка и все прочитанные данные
применяются без промежуточного await и выполняется перерисовка. При отказе чтения
или отменённом намерении прежний активный контекст не заменяется.
Отправка и очистка черновика сверяют `input.dataset.chat` с активным чатом;
асинхронная обработка прикреплённого фото повторяет проверку перед отправкой.
Схема базы, происхождение веток/свайпов и промпты этим не меняются.


### Входной бюджет Prism (F14)

Assembler получает численное положительное окно и неотрицательный резерв ответа.
Доступный вход равен остатку окна за вычетом резерва, без нижнего порога 512.
Резерв, заполняющий окно целиком, и нечисленные/неограниченные значения дают
`report.overflow=true`, `fits=false`; исходные лимиты и `invalidBudget` видны в отчёте.
При принятой сборке `used + reserveTokens <= contextTokens` по проектной оценке.

Обычная отправка сначала собирает предложенный путь с временным узлом пользователя,
до записи и нового Observer. После ожидания предыдущего разбора проверка повторяется.
При отказе дерево остаётся прежним, текст возвращается черновиком. После разбора
сохранённой реплики текущая RP-проверка по-прежнему выполняется перед самой генерацией:
новое состояние может изменить стоимость контекста. Принятая и разобранная реплика
в этом позднем случае сохраняется; это не откат уже выполненной операции.
Проверка фактической Perchance-обёртки добавлена в F15 ниже.


### Стоимость текстового транспорта Perchance (F15)

`perchance.prepareChat(names, messages, opts)` — общая чистая подготовка
`instruction/startWith/stop`. И `inputCost`, и реальная `chat` используют её.
Оценка включает окончательный текст с заголовками, JSON-экранированием,
closing, startWith (в том числе продолжением) и пояснением к вложенному фото.

`prism/service` передаёт в assembler чистый callback `inputCost(messages)`
для выбранного Perchance-провайдера. Сборщик остаётся независимым от транспорта
и проверяет этим callback каждый шаг сокращения; `report.used` отражает конечную
стоимость, `messageUsed` — прежнюю стоимость структурированных сообщений,
`inputFormat` различает Perchance и обычный список сообщений.
Для OpenAI сохраняется прежняя оценка списка сообщений.

Generation формирует transport options до preflight и передаёт те же имена,
closing, continueFrom и вложение в реальный вызов. Режимы: обычный ответ,
новая отправка/правка, regen/continue, opening и инициатива. Предварительная
проверка отправляемого фото учитывает пояснение ещё до записи реплики.
Это оценка текстовой части по `estimateTokens`; точный токенизатор плагина,
его внутренние инструкции и стоимость визуальных токенов недоступны.
Служебные запросы Observer проверены отдельно в F16; бюджет отдельного ассистента проверен в F17 ниже;
собственный budget-конвейер автоматической Memory этим этапом не переработан.


### Preflight Observer и окно модели обработки (F16)

`ctx.contextTokens(provider)` принимает явный провайдер; без аргумента сохраняет
выбор RP. Для API используется настроенное общее окно, для Perchance при autoContext
— его метаданные. Нулевой настроенный размер не подменяется значением 8192.

`providers/simple-request.prepare` используется настоящим `router.simple`;
`budget` считает ту же текстовую форму: инструкция Perchance либо одно user-сообщение
API с накладными расходами, плюс тот же нормализованный резерв вывода.
Observer проверяет полную сформированную инструкцию (правила, источник, недавний
контекст, предыдущие значения и references) перед внешним вызовом. Резерв — 650;
для API это фактический max_tokens. Токены оцениваются проектным счётчиком;
внутренние инструкции и точный токенизатор Perchance не доступны.

При overflow возвращаются статус/численная диагностика и уведомление, освобождается
очередь. Ни модель, ни grounded fallback, ни уточнение одежды не запускаются;
stateEvents/stateStatus и прежние подтверждённые факты не перезаписываются.
Источник не считается обработанным; после изменения окна можно повторить разбор.
Ранний prepareUser проходит ту же проверку. InitialOutfit (650) и WearInquiry (450)
используют этот контракт со своим фактическим RP-провайдером; смысл одежды не меняется.
F12 убрала усечение текущего текста до 4500 символов и ограничение 48 текстовых
фрагментов в evidence-spans; ID T100 и далее поддерживаются. Полный текст получают
обычный Observer, ранний prepareUser и grounded fallback. Размер отдельной адресной
цитаты (420), предел шести выходных событий и отдельные ограничения DRAW не меняются.
`stateStatus.analysedTextChars` — длина полного текста после валидного ответа либо
null при невалидном ответе. Только совпадающее полное покрытие позволяет пропустить
повтор; старая отметка без поля подтверждает лишь текст ≤4500 и ≤48 фрагментов.
Число неразобранных символов при известном частичном покрытии — разность длины
sourceText и analysedTextChars; null означает неподтверждённый разбор, а не ноль
событий. Это метаданные обработки, не физический факт и не гарантия полноты вывода
модели. При overflow прежнее состояние и отметка остаются, повтор возможен.


### Бюджет и принятие запроса ассистента (F17)

`assist.build` считает окончательные messages целиком, включая system и накладные
расходы; для Perchance сервис передаёт тот же чистый inputCost, что использует
реальный транспорт. Минимумы входа 1024/истории 600/выдержки 300 удалены.
Вход равен реальному остатку окна за вычетом фактического резерва ответа.
Дополнительное усечение текста `cardText` и последнего вопроса не допускается:
они либо помещаются, либо получается явный overflow. Состав самого cardText
(Core/custom и прочие непереданные поля) не расширялся — это отдельная F27.

Уступают только старые сообщения разговора с ассистентом, затем старые строки
выдержки RP; это read-only проекции, исходные записи не удаляются.
Report содержит used/messageUsed, резерв/окно, overflow/fits и число оставленных строк.

`assist/service` готовит запрос до добавления пользователя/пустого ответа в запись.
Sampler снимается один раз; `max_tokens=max(настроенное значение,1500)` остаётся
прежним поведением, но тот же размер используется резервом. При preflight-отказе
нет записи, пользовательский текст не очищается. Поле очищается UI-портом только
после принятия и успешной начальной записи; сервис не читает DOM.
Регенерация передаёт ID в сервис и проверяет предложенную историю до замены
прежнего ответа. Lock охватывает чтение подключённого чата и запись; первый
неудачный put не меняет активный разговор. Финальный ответ также записывается
копией до замены отображаемой записи. База и формат бэкапа не меняются.
